# Основания моделей периферии

Проверено 7 ноября 2026. Это источники для анализа, не SDK для сборки.
Эмулятор исполняет локальный `vela_ap.bin` версии 2.3.98; SHA-256 проверяется
профилем. Исходный образ не изменяется.

## Системный блок Cortex-M33

[Arm CMSIS core_cm33.h](https://github.com/ARM-software/CMSIS_5/blob/develop/CMSIS/Core/Include/core_cm33.h)
задаёт расположение SCB/NVIC, маски VTOR/SCR/CCR/SHCSR/CPACR и массивы
приоритетов. Справочная копия `core_cm33.h` сохранена с исходным уведомлением
Apache-2.0. Эмулятор не компилирует и не подключает этот заголовок.

Количество внешних IRQ (78) выведено из 94 записей таблицы векторов
прошивки, а не из инвентаризации чипа. Начальные значения регистров приняты
нулевыми для опыта. Разрядность приоритетов, TrustZone, вход/выход из
исключения и аппаратные эффекты флагов не воспроизведены.

## Контроллеры кэша

В образе функция `0x0c10167c` выбирает базы `0x07ffa000` / `0x07ffc000`.
Она проверяет бит 0 по смещению 0: если сброшен, пишет 1 по смещению 4
и затем 1 по смещению 0; иначе пишет 1 по смещению `0x38`.

Эта последовательность совпадает с `hal_cache_enable` из
[BES HAL в исследовании atc1441](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/hal_cache.c).
Значения смещений сверены с
[reg_cache.h того же проекта](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/reg_cache.h):
0 — управление, 4 — инвалидация, 8 — write-back, `0x38` — очистка с
инвалидацией. Это подтверждение семейства интерфейса, не доказательство
точной ревизии аппаратуры Band 9. Код HAL в проект не копировался.

В нашей модели вся память когерентна сразу, поэтому команды кэша учитываются
как события без изменения данных. Строки кэша, вытеснение, тайминги,
DMA и эффекты шины отсутствуют. Неизвестные операции дают ошибку.

## AON и ревизия чипа

С этими моделями и отдельным хранилищем `0x4008005c=0` старт доходит до
`0x0c10154a`: чтение `0x40080000`, затем сдвиг результата на 16 вправо.
Вызывающий код использует результат при настройке второго кэша.
Сопоставление с [reg_aoncmu_best1503.h](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/best1503/reg_aoncmu_best1503.h)
устанавливает структуру регистра: идентификатор в младших 16 битах,
ревизия — в старших. Регистр только для чтения. Смещение `0x5c` — RAM_CFG;
старт изменяет только поле EMA (биты 0..2). Модель поддерживает именно эти
операции; остальные поля и аппаратные эффекты не реализованы.

Вызов по адресу `0x0c1016ac` сравнивает ревизию с 13 и записывает в
управление второго кэша по смещению 8 значение `0xa` при ревизии ≤13,
либо `2` при >13 (если исходное значение нулевое).
В `cache_control.py` разрешён дополнительно наблюдаемый бит 3.
Правильное значение CHIP_ID физического браслета не измерено. Сценарий
`startup-ram.debug` явно проверяет обе ветки значениями `0x000d0000` и
`0x000e0000`; младший идентификатор 0 тоже условный.

## Исполнение из RAM

Сам образ задаёт перенос flash `[0x2c1019a4, 0x2c10c3fc)` в
RAM начиная с `0x2005c1c0`. После переноса он переходит через литерал
по `0x0c101810` на `0x00260089` (Thumb). Байты по этому адресу должны
соответствовать RAM `0x20060088`. Это подтверждается
[картой памяти BES из исследования atc1441](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/best1503/plat_addr_map_best1503.h):
data-RAM `0x20000000`, исполняемое зеркало `0x00200000`.
Та же карта связывает AON с `0x40080000`, IOMUX с `0x40086000`.
Это сопоставление с исследовательской картой, не полная спецификация чипа.

В стенде оба диапазона используют общий буфер через `mem_map_ptr` Unicorn.
Изменения RAM помечают переводы кода как устаревшие. Их сброс выполняется
между вызовами Unicorn, до дальнейшего исполнения из зеркала. Такой порядок
нужен в установленном Windows runtime: сброс переводов из memory-hook
приводил к завершению процесса. Гостевые инструкции при синхронизации
не пропускаются. Проверены повторный вызов изменённого кода, гостевая запись,
точки останова, восстановление снимка и откат частичной ошибочной записи.

## IOMUX и таймеры

[BES reg_iomux_best1503.h](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/best1503/reg_iomux_best1503.h)
сопоставляет поля выбора маршрутов групп P0..P9 и битовые поля подтяжек.
Стартовый код `0x00260088` перебирает 80 выводов; по адресу `0x0026004c`
следует дополнительная настройка группы P4. Из нулевого экспериментального
состояния получаются маршруты 15 и pull-down для P1_0..P1_7, маршруты 7
для P4_0..P4_5, запись `0x3c00` в регистр `0xac`.
Последняя маска не совпадает с описанием SDK: модель хранит только наблюдаемые
биты, не приписывая им название UART/SPI. В `0xc4` разрешена только
наблюдаемая нулевая запись. Полная электрическая модель отсутствует.

Поле bit 18 регистра AON CLK_OUT (`0x4008001c`) сверено с ранее указанным
заголовком AON. Прошивка очищает его в функции `0x0c101040`; поддерживается
только это поле конфигурации, без переключения частот.

[BES reg_timer.h](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/reg_timer.h)
задаёт Load, Value, Control, IntClr, RIS и MIS. Значение `0x82` выбирает
включённый 32-битный счёт без IRQ, делителя и периодического режима.
[BES hal_timer.c](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/hal_timer.c)
содержит такую инициализацию и чтение времени как отрицания текущего счётчика.
Модель реализует канал 0 двух блоков; неподдерживаемые режимы и каналы
вызывают ошибку. Флаг RIS при достижении нуля и его очистка основаны на
[Arm SP804 TRM](https://documentation-service.arm.com/static/5e8e2102fd977155116a4aef).
Это согласуемая абстракция интерфейса, не доказательство полного совпадения
периферии BES с SP804.

Виртуальный входной такт привязан к инструкции, а не к чтению регистра или
времени компьютера. Тик синхронно откатывается вместе с ошибочной инструкцией;
снимки сохраняют всё состояние. Подтверждены цикл ожидания, одинаковый результат
при `step`/`run`, остановка таймера, переход через ноль и восстановление снимка.
Реальные частоты и связь таймеров с CMU ещё не реализованы.

## Предыдущая и текущая границы загрузки

Обе экспериментальные ветки запускают настоящий перенесённый код.
Остановка — PC `0x00260092`, запись `0xffffffff` в `0x40086008` (IOMUX).
Это сохранённая граница сценария без модели IOMUX. Результаты двух веток:
`results/debug-startup-revision13.json` и `results/debug-startup-revision14.json`.
Старый сценарий `startup-core.debug` сохраняет прежнюю границу на CHIP_ID.

Новый `startup-io.debug` проходит эту точку и включает оба таймера.
CMU PERIPH_CLK (`0x4000005c`) содержит поле выбора быстрых источников,
сверенное с [reg_cmu_best1503.h](https://github.com/atc1441/MiBand10-BES2700iMP-BEST1503-Hacking/blob/main/bes2700impForDisplayRe/platform/hal/best1503/reg_cmu_best1503.h).
Функции прошивки `0x00264f50` и `0x00264f6a` устанавливают биты 10 и 11,
сохраняя предыдущее значение. Модель поддерживает только эти биты;
остальные регистры CMU, PLL, тактирование и сбросы не имитируются.
Оба таймера пока получают одинаковый виртуальный входной такт, независимо
от выбора источников. Это ограничение явно записано в отчёте.

Следующая остановка: PC `0x0c1015fc`, чтение AON BOOTMODE `0x40080038`.
Регистр режима/причины загрузки не заменён нулём; его семантику предстоит
моделировать отдельно. С нуля — 85 925 / 85 926 инструкций для
экспериментальных ревизий 13 / 14. Отчёты `debug-startup-io-revision*.json`
не содержат автоматически добавленных заглушек неизвестных регистров.
